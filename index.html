Declarative Secret Delivery for AI Microservices on Kubernetes

Rahul Kaura · Forward Deployed Engineering, Uniphore

Abstract

AI platforms depend on more credentials than most services: model provider keys, vector and relational database passwords, identity provider client secrets and tokens for internal APIs. Empirical studies of developer practice show that secrets are routinely stored in source, copied between environments and rotated rarely, and that deployment-time handling is among the hardest problems developers report. This report describes an architecture that moves an AI platform's credentials to declarative delivery with the External Secrets Operator (ESO): secret values live only in a central encrypted store, version control holds references, and a controller continuously reconciles them into per-service Kubernetes Secrets. We give a threat model and requirements, describe the reconciliation semantics the design relies on, derive a timing condition for zero-downtime rotation, analyze failure modes and their blast radius, and describe how dependency tracing was used to plan the migration. We close with an evaluation method and open problems, including short-lived credentials and policy-as-code enforcement.

1. Introduction

A single request on an enterprise AI platform can cross an identity provider, an API gateway, a retrieval store, several model endpoints and an agent orchestration layer. Each hop authenticates, so each hop needs a credential. When those credentials reach workloads through manual steps (values pasted into kubectl create secret, copied between CI variables, or carried in environment files) the platform inherits three problems. Values drift between environments. Nobody can say with confidence which services consume a given key, so rotation turns into a coordinated outage. And secrets created outside version control have no review trail.

These are not unusual failures. A grey-literature review of 54 practitioner sources identified 24 secret-management practices across six categories, including keeping secrets out of source code, storing them in external secret managers, limiting exposure with short-lived credentials, and managing secrets separately per deployment environment [2]. A companion study of 779 Stack Exchange questions found 27 recurring developer challenges, with storing and versioning secrets during deployment among the most common [3]. The goal of this work was to put those recommended practices into the platform itself, so following them is the default rather than a discipline each team has to remember.

This report makes four contributions:

  • A threat model and set of requirements for credential delivery on a multi-tenant AI platform (Section 3).
  • An ESO-based architecture that maps each requirement to a concrete mechanism and to the practices catalogued in [2] (Section 4).
  • A timing condition for rotation without downtime, derived from the controller's reconciliation semantics (Sections 5 and 6).
  • A failure-mode analysis and a dependency-tracing method used to order the migration (Sections 7 and 8).

2. Background and related work

2.1 Reconciliation in Kubernetes

Kubernetes is built from controllers that observe the cluster, compare actual state to a declared desired state, and act to close the difference. Burns et al. trace this design from Borg and Omega and argue that level-triggered reconciliation, as opposed to one-shot imperative commands, is what lets large systems recover from partial failure without manual intervention [1]. Declarative secret delivery applies the same idea to credentials: the declared state is "this namespace should hold this key from this store," and a controller keeps re-establishing it.

2.2 Empirical studies of secret management

Basak et al. classify practices into six groups: keeping secrets out of source, storing them securely, limiting exposure, avoiding accidental commits, managing secrets in deployment, and organizational enforcement [2]. Their follow-up study of developer questions finds that the most common recommended fixes are moving secrets into configuration templates, adopting secret management tools at deployment time, and using environment variables, while a growing share of questions go unanswered [3]. SecretBench provides a labeled dataset of real secrets found in public repositories to evaluate detection tools [4]. Detection matters, but it is reactive. This work targets the deployment and storage categories, where a platform can prevent the leak instead of finding it later.

2.3 Misconfiguration in Kubernetes artifacts

Rahman et al. study security misconfigurations in open-source Kubernetes manifests and find that insecure defaults and exposed sensitive data are common in real deployments [6]. Minna, Massacci and Tuma analyze Helm charts from Artifact Hub with multiple static analyzers and test whether LLMs can propose fixes that pass the analyzers' policies on re-scan [5]. Both lines of work point to the same lesson: secrets embedded in deployment artifacts are hard to audit and easy to get wrong, which favors designs where manifests carry only references.

2.4 Zero trust

NIST's zero trust architecture guidance treats every request as untrusted until authenticated and authorized, and calls for least-privilege access scoped per resource [7]. In a cluster, that translates into scoping each workload's ability to read secrets to exactly the paths it needs, rather than granting a broad credential to a shared operator.

3. Threat model and requirements

Assets. Model provider API keys, data store credentials, identity provider client secrets and internal service tokens. Several of these carry direct cost exposure (a leaked model key can be billed against) as well as data exposure.

Adversary or failureCapabilityWhat it can reach in the manual setup
Leaked repository or CI logRead access to code, manifests or build outputAny secret committed or echoed during a build
Compromised workloadCode execution in one podThat pod's secrets, plus any shared secret bundle mounted alongside
Over-privileged operator identityRead access to the central storeEvery secret the identity is allowed to list
Operator errorWrong value, wrong environment, missed rotationOutages across every consumer of the shared value

From this we set six requirements:

  1. R1 · No values in Git. Manifests may reference secrets but never contain them.
  2. R2 · Least privilege. A workload can read only the remote paths it consumes.
  3. R3 · Encryption on every leg. At rest in the store, in transit to the cluster, at rest in the cluster datastore.
  4. R4 · Rotation without downtime. Replacing a credential must not drop traffic.
  5. R5 · Contained failure. A bad reference or a store outage must not cascade across unrelated services.
  6. R6 · Observability. Every sync failure is visible before a request fails because of it.

4. Architecture

ESO introduces custom resources that describe where a secret comes from without containing it [8]. A SecretStore (namespaced) or ClusterSecretStore (cluster-wide) describes how to authenticate to the external provider. An ExternalSecret names the remote keys to fetch, how to map them into a target Kubernetes Secret, and how often to refresh. A generalized example:

apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: inference-gateway-creds
  namespace: ai-inference
spec:
  refreshInterval: 1h
  secretStoreRef:
    kind: ClusterSecretStore
    name: central-store
  target:
    name: inference-gateway-creds
    creationPolicy: Owner
  data:
    - secretKey: MODEL_API_KEY
      remoteRef:
        key: ai-inference/model-provider
        property: api_key

The design decisions, and the requirement and documented practice each one serves:

DecisionRequirementPractice category in [2]
Manifests carry remoteRef keys only; values never enter Git or CIR1Keep secrets out of source
Store paths namespaced by consumer; store auth scoped per namespaceR2Limit exposure
Encrypted provider store, TLS to the operator, encryption at rest in the cluster datastore [9]R3Store secrets securely
One ExternalSecret and one target Secret per consuming serviceR5Manage secrets in deployment
Separate store paths per environment, same manifest shapeR1, R5Different secrets per environment
Sync status exported to monitoring with alertingR6Audit and organizational enforcement

The one-resource-per-consumer rule is the least obvious choice. A shared bundle (one Secret holding every key a namespace might need) is simpler to write but violates R2, because every pod that mounts it can read every key, and violates R5, because one bad key fails every consumer of the bundle.

5. Reconciliation semantics

The design depends on four behaviors of the controller [8]:

  • Periodic refresh. Each ExternalSecret is re-synced on its refreshInterval, so a value changed in the store reaches the cluster within one interval.
  • Ownership. With creationPolicy: Owner, the target Secret is owned by the ExternalSecret and removed with it. This keeps environments clean but must be a deliberate choice during migration, when a pre-existing Secret might otherwise be adopted or deleted.
  • Status reporting. Each resource reports its own readiness condition, so a failed sync is attributed to exactly one consumer.
  • Last known good. When the provider cannot be reached, the existing target Secret is left in place rather than cleared, so running workloads keep working.

From these, the worst-case time for a new value to be in use by a consumer is bounded by

Tprop ≤ r + treload

where r is the refresh interval and treload is how long the consumer takes to pick up the change. For a workload that reads a mounted file on each use, treload is the kubelet's volume update delay. For a workload that reads environment variables, the value is fixed at process start, so treload is the duration of a rolling restart. This distinction drove most of the per-service rotation plans.

6. Rotation protocol

Zero-downtime rotation requires an overlap window during which both the old and the new credential are accepted by the provider. Let W be that window. Rotation is safe when

W > r + treload + tverify + m

where tverify is the time to confirm every consumer is healthy on the new value and m is a safety margin. If the provider does not support two valid credentials at once, the alternative is a blue-green swap at the consumer level, which is slower and is reserved for those providers.

rotate(secret_path, consumers):
    new = provider.issue_credential()          # old stays valid
    store.write(secret_path, new)
    wait_until(all(c.secret_version == new.version for c in consumers),
               timeout = r + t_reload)
    for c in consumers where c.reads_env_vars:
        rolling_restart(c, max_unavailable = 0)
    assert all(healthy(c) and c.authenticates_with(new) for c in consumers)
    provider.revoke(old)                       # only after verification

Revocation is the last step and is gated on verification, never on time alone. A rotation that stalls leaves the old credential valid and raises an alert; it does not break traffic.

7. Failure analysis

FailureEffect with shared bundlesEffect with per-consumer resourcesDetection
Remote key missing or renamedBundle fails to sync; every consumer affected on next restartOne consumer's sync fails; others unaffectedReadiness condition on that resource
Store denies accessAll namespaces using the shared identity failOnly the namespace whose scope changedSync error alert
Store unreachableNew pods cannot start if secrets are fetched at bootExisting Secrets retained; running pods continueOperator and store health checks
Wrong value writtenAll consumers break togetherOnly consumers of that path break; rollback is a store revertConsumer health checks after sync
Operator downNot applicableNo new syncs; existing Secrets keep workingController liveness alert

In every row, the per-consumer design either confines the failure to one service or degrades to "no updates" rather than "no service." That is the property R5 asks for.

8. Dependency tracing

The largest risk in the migration was not the operator but not knowing who used what. Before moving anything, each credential was traced end to end and recorded as a graph with three node types (service, secret, provider) and edges for "consumes" and "authenticates to." For each service the trace recorded how the secret is read (file or environment variable), which downstream API or model endpoint accepts it, and what fails if it is wrong.

That graph did three jobs. It ordered the migration, moving leaf services first and shared dependencies such as the authentication path last. It exposed shared credentials that needed to be split before least privilege was possible. And it became the input to each rotation plan, since treload depends on how each consumer reads its secret.

9. Evaluation method

We evaluate the design operationally rather than with a benchmark. The measures that matter, and how each is collected:

  • Manual secret count: Secrets in the cluster with no owning ExternalSecret. The target is zero outside an allowlist.
  • Sync health: Failed syncs per day and time to resolve, from controller status.
  • Time to rotate: From issuing a new credential to revoking the old one, per secret class.
  • Rotation-caused errors: Authentication failures at consumers during a rotation window. The target is zero.
  • Blast radius: Number of services that fail when a single remote key is broken in a staging drill.

Measured values are omitted because they come from an internal production environment. Environment names, store paths and provider details in this report are generalized.

10. Limitations and future work

Long-lived credentials. Many AI providers still issue static API keys. The design rotates them safely but cannot make them short-lived. Where providers support it, dynamically issued, short-lived credentials bound to workload identity would remove most of the rotation burden, which is the "limit exposure" practice in [2] taken further.

Read auditing. The store logs which identity fetched a value, but not which pod used it afterward. Linking the two would make incident response faster after a suspected leak.

Policy as code. Nothing yet prevents a new ExternalSecret from requesting a path outside its namespace's intended scope beyond what store permissions allow. Admission-time policy checks would close that gap. Work on LLM-proposed fixes for Kubernetes and Helm misconfigurations [5] suggests such checks could also propose corrections, though the generated fixes would still need verification by re-scanning.

Structure-Preserving Document Ingestion for Enterprise RAG

Rahul Kaura · Forward Deployed Engineering, Uniphore

Abstract

Retrieval-augmented generation assumes that a retrieved passage carries the information needed to answer a question. Enterprise compliance documents break that assumption: the meaning of a clause depends on the section above it, a table cell depends on merged headers, and exceptions live in footnotes. Fixed-size chunking discards this structure, and language models are known to use long, unstructured contexts unevenly. We describe a production ingestion pipeline that converts heterogeneous business files into a typed document tree, resolves table headers including merged cells, generates abstractive summaries along the document's own hierarchy, validates every record against a JSON schema, and indexes chunks together with their outline path. We relate each stage to prior work on layout-aware models, table extraction datasets, hierarchical retrieval and constrained decoding. We also describe the benchmark used to choose between graph-based and transformer-based parsers, using text, table-structure and tree-level fidelity, latency, schema validity and compute cost, and a selection rule that picks the cheapest parser meeting fidelity floors.

1. Introduction

Retrieval-augmented generation (RAG) pairs a parametric model with a non-parametric index so the model can ground its output in retrieved text [1]. In practice, retrieval quality is limited less by the retriever than by what was indexed. Most pipelines split extracted text into fixed-length windows. For compliance search that is the wrong unit. A sentence like "this requirement does not apply" is useless without the heading that says which requirement, and a value from a table row is wrong if it is attached to the wrong column header.

Simply passing more context to the model is not a reliable fix. Liu et al. show that model accuracy on multi-document question answering drops when the relevant passage sits in the middle of a long context rather than at the start or end [2]. Context has to be small and correct, which means it has to be structured before it reaches the index.

Before this pipeline, preparing compliance files for search required manual cleanup. That did not scale to large repositories and delayed downstream queries. This report contributes:

  • A typed intermediate representation (IR) that decouples parsing from everything downstream (Section 3).
  • A production pipeline built on that IR, including a header-resolution procedure for merged table cells (Sections 4 and 5).
  • A design for hierarchy-aligned summaries and path-aware chunks, contrasted with clustering-based hierarchical retrieval (Sections 6 and 8).
  • A schema-validation loop and the reasoning for post-hoc validation over constrained decoding in this setting (Section 7).
  • A reproducible benchmark and selection rule for choosing a production parser (Section 9).

2. Related work

2.1 Layout-aware document models

LayoutLM introduced joint pre-training over text and 2-D position, showing that layout is a strong signal for document understanding [5]. LayoutLMv3 unifies text and image masking in pre-training and applies to both text-centric and image-centric document tasks [6]. Both build on the transformer architecture [14]. Nougat goes further, transcribing page images of academic documents directly into markup with an encoder-decoder transformer [11]. These are the transformer-based family in our benchmark.

2.2 Graph-based document understanding

Graph approaches model a page as nodes (words, lines or layout entities) connected by spatial and reading-order edges. Doc2Graph builds such graphs and applies graph neural networks to tasks including key-value linking and table detection, independent of document type [7]. Graph methods tend to give explainable, predictable decisions because relations are explicit, which matters when an extraction has to be audited.

2.3 Layout and table datasets

DocLayNet provides human-annotated layout labels across diverse document categories, which makes it a better training source for enterprise documents than corpora drawn from a single domain [8]. PubTables-1M contributes nearly a million annotated tables and, importantly for us, a canonicalization procedure that merges over-split header cells so each table has one unambiguous structure; the authors report this changed a large share of complex tables [9]. Zhong et al. introduced the tree-edit-distance-based similarity metric (TEDS) for comparing predicted and true table structure [15], which we adopt for table fidelity.

2.4 End-to-end conversion toolkits

Docling combines a layout model trained on DocLayNet with TableFormer for table structure, matches predictions back to the PDF's own text cells rather than re-transcribing them, and assembles a typed document that can be exported to JSON or Markdown [10]. Our IR follows the same principle of a typed, export-neutral document object between parsing and use.

2.5 Hierarchical and structure-aware retrieval

RAPTOR recursively embeds, clusters and summarizes chunks into a tree, then retrieves across levels; the authors find that searching a collapsed version of the tree under a token budget works better than top-down traversal [3]. Jimeno Yepes et al. show on financial reports that chunking by document element type, instead of by fixed size or paragraph, substantially improves RAG and removes the need to tune chunk size by hand [4]. Our design sits between the two: like [4] it uses the document's real elements, and like [3] it adds summaries at higher levels of a tree, but the tree is the document's own hierarchy rather than one learned by clustering.

2.6 Structured generation

Willard and Louf reformulate guided generation as transitions in a finite-state machine over the vocabulary, making regex and grammar constraints efficient at decode time [12]. JSONSchemaBench evaluates six constrained decoding frameworks on about 10K real-world JSON schemas along efficiency, constraint coverage and output quality, and finds meaningful gaps in coverage across frameworks [13]. This motivates the validate-and-retry design in Section 7.

3. Problem formulation

A source document D is converted into a rooted, ordered tree T = (V, E). Each node v ∈ V has a type τ(v) ∈ {document, section, paragraph, list, table, row, cell, footnote, figure}, text x(v), a source anchor (page and bounding box), and type-specific attributes. Edges encode containment. Cells additionally carry resolved row and column header paths. Footnotes carry a reference edge to the node that cites them.

The outline path of a node is the sequence of section titles from the root to its nearest section ancestor:

path(v) = ⟨ title(s1), title(s2), …, title(sk) ⟩

The IR is the only contract between parsing and the rest of the system. Any parser that emits a valid T can be swapped in without changing summarization, validation or indexing. This is what makes the comparison in Section 9 fair: every parser is scored on the same downstream output.

4. Pipeline

  1. Layout parsing. Each page yields typed layout elements with positions: headings, paragraphs, list items, tables, cells, footnotes, figures and captions.
  2. Tree construction. Elements are ordered by reading order and nested by heading level, numbering patterns ("4.2.1") and indentation. Footnote markers are linked to their footnotes.
  3. Table normalization. Header cells are resolved for every body cell, including merged and multi-row headers (Section 5).
  4. Outline and summaries. Section summaries are generated bottom-up along the tree (Section 6).
  5. Schema validation. Every emitted record is validated; failures are regenerated with the error message as feedback (Section 7).
  6. Indexing. Chunks are formed from tree nodes and stored with their outline path and summary (Section 8).

5. Table normalization

Merged header cells are the most common source of silent extraction errors: text is extracted correctly but attached to the wrong header. Following the canonicalization idea in PubTables-1M [9], we first expand every spanning cell into the grid positions it covers, then resolve each body cell's full header path:

resolve_headers(table):
    G = expand_spans(table)              # each spanning cell fills every grid slot it covers
    H_rows = detect_header_rows(G)       # top rows that are mostly text and repeat across columns
    H_cols = detect_header_cols(G)       # left columns that act as row labels
    for cell in body_cells(G):
        col_path = [G[r][cell.col].text for r in H_rows if G[r][cell.col].text]
        row_path = [G[cell.row][c].text for c in H_cols if G[cell.row][c].text]
        cell.col_header = dedupe_adjacent(col_path)   # merged parents appear once
        cell.row_header = dedupe_adjacent(row_path)
    return G

Each body cell is then serialized with its headers attached, for example Retention period › Backups › Region B: 35 days, so the value never travels without its meaning. Tables are scored with TEDS [15] against hand-labeled ground truth in the benchmark.

6. Hierarchy-aligned outlines and summaries

Long sections are hard to retrieve by keyword because the relevant terms are spread across paragraphs. We generate an abstractive summary for each section node, bottom-up: leaf sections are summarized from their text, and parent sections are summarized from their own text plus their children's summaries. A parent summary therefore describes its whole subtree in a bounded number of tokens.

This resembles RAPTOR's recursive summarization [3] with one deliberate difference. RAPTOR builds its hierarchy by clustering chunk embeddings, which is the right choice when a corpus has no reliable structure. Compliance documents do have structure, authored on purpose, and auditors cite it ("Section 4.2"). Using the document's own hierarchy keeps every summary traceable to a citable section, which a clustered summary spanning unrelated sections would not be.

7. Schema-constrained output

Every record leaving the pipeline conforms to a fixed schema. A simplified version:

{
  "doc_id":   "string",
  "node_id":  "string",
  "type":     "section | paragraph | table_cell | footnote",
  "path":     ["string"],
  "text":     "string",
  "summary":  "string | null",
  "headers":  {"row": ["string"], "col": ["string"]},
  "source":   {"page": "integer", "bbox": ["number", "number", "number", "number"]}
}

There are two ways to guarantee conformance. Constrained decoding restricts the model's tokens at generation time [12]. Post-hoc validation generates freely, validates, and retries with the validator's error as feedback. JSONSchemaBench shows that constraint coverage differs substantially across decoding frameworks [13], and the pipeline has to work across more than one model backend. We therefore validate every record regardless of how it was generated, and use constrained decoding opportunistically where the backend supports the needed schema features.

emit(node, max_attempts = 3):
    for attempt in 1..max_attempts:
        rec = generate_record(node, feedback = last_error)
        ok, last_error = validate(rec, SCHEMA)
        if ok: return rec
    quarantine(node, last_error)        # never indexed; surfaced for review

Records that never validate are quarantined, not indexed. A missing record is visible and fixable; a malformed one silently degrades retrieval.

8. Path-aware indexing

Chunks are formed from tree nodes rather than from token windows, following the element-based approach of [4]. Each indexed unit is a triple

chunk(v) = ⟨ path(v), x(v), summary(parent(v)) ⟩

The path and parent summary are prepended to the text that is embedded and to the text passed to the model. A retrieved paragraph therefore arrives as "Policy › 4 Data Retention › 4.2 Exceptions: …" together with a one-paragraph description of what Section 4 covers. This keeps each context short, which matters given the position sensitivity reported in [2], while still carrying the context the passage depends on.

9. Parser benchmark

9.1 Corpus

A fixed evaluation set was stratified by known failure mode: nested tables, merged header cells, footnote-heavy pages, multi-column layouts and deep numbered hierarchies. Each document has hand-labeled ground truth for text, table structure and section tree. The set, parser versions, configuration and hardware were frozen so any result can be re-run.

9.2 Metrics

DimensionMetricWhat it catches
Text fidelityNormalized edit distance and token-level F1 against ground truthDropped, duplicated or garbled text
Table fidelityTEDS [15] and cell-level header accuracy after Section 5Values attached to the wrong header
Tree fidelityTree edit distance between predicted and true section trees, normalized by sizeWrong nesting; sections merged or split
LatencyMedian and 95th-percentile seconds per pageParsers too slow for repository-scale backfills
Inference compatibilityShare of records valid on first attempt; share exceeding the token budgetOutput the downstream model cannot use without repair
CostCompute cost per thousand pages at production batch sizesParsers that are accurate but unaffordable at scale

9.3 Selection rule

Averaging these into one score hides the failure that matters most. Instead we set a minimum acceptable value fmin for each fidelity metric and choose

p* = argminp ∈ P cost(p)   subject to   fidelityj(p) ≥ fmin,j for every j, and latencyp95(p) ≤ L

That is, the cheapest parser that clears every fidelity floor and the latency budget. Because metrics are computed per stratum, the same rule can choose different parsers for different document types.

10. Observations

  • No parser dominated. The tradeoff between fidelity and cost depended on the document type, which is why the selection rule is applied per stratum rather than once.
  • Merged headers were the main silent error. Most table errors were correct text attached to the wrong header, which text-level metrics alone do not catch. TEDS plus header accuracy did.
  • Validation earned its cost. The validate-and-retry loop kept malformed records out of the index; quarantine made the remainder visible for review instead of silently degrading retrieval.
  • The IR made iteration cheap. Because downstream stages read only the tree, re-running the benchmark after a parser update required no pipeline changes.

Quantitative results are omitted because they were measured on internal customer documents.

11. Limitations and future work

Threats to validity. Ground truth was labeled by a small number of annotators, so structural labels for ambiguous layouts reflect their judgment. The evaluation set is stratified for hard cases and over-represents them relative to a real repository, which biases fidelity downward and cost comparisons toward the hard tail.

Scanned documents. Scanned inputs depend on OCR quality, which the pipeline does not control. Page-to-markup models such as Nougat [11] are a candidate path for this subset.

Retrieval-level evaluation. This benchmark measures parsing. The next step is end-to-end evaluation of answer quality on a fixed question set, so parser choice can be tied directly to the metric users care about.

Routing. A lightweight classifier could route each file to the cheapest parser likely to clear the fidelity floors for its document type, applying the Section 9.3 rule per file instead of per stratum.

Agentic Incident Response with Change-Aware Anomaly Detection

Rahul Kaura · AI/ML Engineering, Empirik AI (formerly Manifest)

Abstract

Many production incidents begin with a change: a deployment, a permission update, a configuration edit. The evidence is spread across Kubernetes events, application performance metrics, infrastructure monitors and logs, and each tool alerts on its own. Recent work shows that large language models can recommend root causes and mitigations for cloud incidents, but also that tool-using agents hallucinate, loop on complex cases, and raise false positives when nothing is wrong. We describe an autonomous incident-response agent, built with LangGraph, LangChain, the Model Context Protocol and the OpenAI API, that is designed around those failure modes. Unsupervised detection with Isolation Forest and rolling-baseline thresholds runs on log telemetry; a sliding-window correlator requires agreement across independent signal sources before confidence rises; and the agent itself is an explicit state machine in which the model gathers evidence and explains, while deterministic rules decide whether any production change is made. Automated rollback is limited to high-risk actions with a recoverable prior state. We formalize the detection and correlation steps, describe the agent's states and tool scopes, and give an evaluation method based on historical replay and fault injection.

1. Introduction

Alerting tools are good at saying that something looks wrong and poor at saying why. They are worse at connecting a symptom in one tool to its cause in another. An on-call engineer ends up doing that correlation by hand: a latency spike in APM, a restart loop in Kubernetes events, a permission change logged an hour earlier. Each tool's alert is individually noisy; together they are often decisive.

Large language models are a natural fit for the "explain why" step. They can read heterogeneous telemetry, relate it to past incidents and write a summary an engineer can act on. They are a poor fit, on their own, for the "decide what to change in production" step. The system described here separates those two jobs explicitly.

This report contributes:

  • A formulation of change-aware detection that combines Isolation Forest scores with rolling-baseline thresholds over windowed telemetry (Section 4).
  • A cross-source correlation rule that raises confidence only when independent signals agree in time (Section 5).
  • An agent architecture that confines the model to evidence gathering and explanation, with scoped tools and rule-based decisions, motivated by failure modes reported in prior agent studies (Section 6).
  • A conservative rollback policy with explicit preconditions and an audit record (Section 7).
  • An evaluation method combining historical replay, shadow mode and fault injection (Section 9).

2. Related work

2.1 Unsupervised anomaly detection

Isolation Forest detects anomalies by isolating points with random axis-parallel splits; anomalous points are isolated in fewer splits, which gives a fast, label-free score that scales to high-dimensional data [1]. Extended Isolation Forest replaces axis-parallel splits with random hyperplanes to remove artifacts that the original method produces along feature axes [2]. Pang et al. survey deep anomaly detection and highlight the scarcity of labeled anomalies and the cost of false positives as central problems [3]. Both apply directly to production incidents, where labels are rare and alert fatigue is the main operational cost.

2.2 LLMs for incident management

Zhang et al. survey AIOps for failure management in the era of LLMs, organizing work by task (detection, localization, root cause analysis and mitigation) and by data source [4]. Ahmed et al. study about 44,000 incidents across roughly 1,800 Microsoft cloud services and find that fine-tuned GPT-3.x models produce root-cause and mitigation recommendations that incident owners rate higher than smaller baselines; they also find that automatic text metrics correlate poorly with those human judgments [5]. RCACopilot pairs engineer-written incident handlers, which collect diagnostic data automatically for each alert type, with an LLM that predicts a root-cause category using retrieved past incidents as demonstrations; it reports a micro-F1 of 0.766 on 653 incidents [6].

2.3 Tool-using agents for operations

ReAct interleaves reasoning traces with tool calls so a model can gather information before answering [9]. Roy et al. apply a ReAct agent to root cause analysis on 500 sampled incidents. It hallucinates root causes far less than retrieval and chain-of-thought baselines but is slightly less accurate overall, and in a case study it often hits its iteration limit on complex incidents [7]. AIOpsLab provides an environment that deploys microservices, injects faults, generates load and exposes an agent-cloud interface across 48 problems; the authors find agents struggle most with root cause analysis and mitigation, waste steps on redundant actions, mishandle verbose telemetry, and frequently report faults that are not there [8].

2.4 What this work takes from them

Three design choices follow directly from this literature. From [6]: collect diagnostics with deterministic, per-alert procedures, and let the model reason over the result rather than decide what to collect from scratch. From [7] and [8]: bound the agent's steps, keep telemetry summarized before it reaches the model, and do not let a model's belief that a fault exists be sufficient to change production. From [3]: treat false positives as the primary cost, which is why confidence requires multi-source agreement.

The task is: given these streams, (a) flag time windows in which the system's state changed abnormally or without authorization, (b) attach the most likely causal change and supporting evidence, and (c) either remediate, escalate to a human, or close the alert as noise.

4. Detection

4.1 Windowing and features

Each stream is cut into windows of length Δ with stride s < Δ, so a burst near a boundary is seen whole in at least one window. For window t, a feature vector xt is built from log and event data: counts per event type, error-to-total ratios, the rate of change-related events, the number of distinct resources and principals touched, and the share of actions by principals not seen in the trailing baseline.

4.2 Isolation Forest score

Isolation Forest builds an ensemble of random isolation trees on sub-samples of size ψ. For a point x, let h(x) be its path length in a tree and E[h(x)] its mean across trees. The anomaly score is [1]

s(x, ψ) = 2−E[h(x)] / c(ψ),    c(n) = 2H(n−1) − 2(n−1)/n

where H(i) is the harmonic number, approximately ln(i) + 0.5772. Scores near 1 indicate points that isolate quickly. The forest is refit on a trailing baseline so "normal" tracks gradual growth in traffic and fleet size.

4.3 Rolling-baseline thresholds

Alongside the forest, key metrics are compared with their own recent history. Written as a robust z-score over a trailing window,

zt = (mt − medianB) / (1.4826 · MADB)

where B is the baseline window and MAD is the median absolute deviation. Median and MAD are used instead of mean and standard deviation because a single past incident in the baseline would otherwise inflate the threshold and hide the next one.

4.4 Why two detectors

The forest is good at multivariate novelty, such as an unusual combination of principal, resource and action, but it gives no reason. Thresholds are interpretable but see one metric at a time. They fail differently, so a window that trips both is stronger evidence than one that trips either, and the threshold that fired gives the agent a concrete starting point.

5. Cross-source correlation

Let S be the set of signal sources and ai,t ∈ [0, 1] the normalized anomaly strength of source i in window t, restricted to resources related to a candidate change (the same workload, its dependencies, or the same principal). Confidence is

conft = ∑i∈S wi · ai,t,    with action allowed only if conft ≥ θ and |{i : ai,t > ε}| ≥ 2

The second condition is what reduces noise. A single source, however strong, can raise an alert for a human but can never on its own trigger an automated action. Weights wi reflect how often each source has been right in past incidents and are kept simple and inspectable.

6. Agent architecture

The agent is a LangGraph state graph, not an open-ended loop. Every state, transition and tool call is explicit and logged, and the graph has a hard step budget, which addresses the looping behavior reported in [7]. Within states, the model follows a reason-then-act pattern [9].

StateInputModel's jobTools (via MCP)Exit
TriageCorrelated window, confidenceSummarize what fired and whereNoneInvestigate or close
GatherTriage summaryChoose which evidence to pull nextRead-only: recent changes, k8s events, metric queries, log searchEnough evidence or step budget reached
HypothesizeCollected evidenceName the most likely causal change and cite the events it relies onNoneHypothesis with citations
DecideHypothesis, confidence, change metadataNone (deterministic rules)NoneAct, escalate or close
ActApproved actionNoneWrite-scoped: rollback of the named resource onlyVerified or escalated
EscalateEverything aboveWrite the on-call summaryPaging and ticketingDone

Tool scoping. Tools are exposed through the Model Context Protocol with read-only scopes by default. The single write-capable tool exists only in the Act state, and only for the resource named in the approved decision. The model cannot reach it from Gather or Hypothesize.

Summarized telemetry. Raw logs and metric series are summarized before they reach the model (top-k error signatures, deltas against baseline, the change list for the window). AIOpsLab reports that agents mishandle verbose telemetry [8]; summarization keeps context short and reduces that failure.

Grounded hypotheses. A hypothesis must cite specific events by identifier. If it cites none, or cites events that do not exist in the gathered evidence, it is rejected and the agent escalates. This targets the hallucinated root causes measured in [7].

7. Rollback policy

The model explains; code decides. Automated rollback is permitted only when every precondition holds:

may_rollback(change, conf, sources):
    return  change.risk_class in HIGH_RISK           # critical deployments, privileged IAM grants
        and change.prior_state.is_restorable          # exact previous spec or policy is stored
        and conf >= THETA_ACTION
        and count(s for s in sources if s.strength > EPS) >= 2
        and change.age <= MAX_AGE                    # recent enough that rollback is safe
        and not change.has_dependent_changes_after    # nothing built on top of it since

Every rollback writes an audit record containing the triggering window, the confidence and contributing sources, the hypothesis with its cited events, the exact prior state restored, and post-rollback verification results. If verification fails, the agent does not try again; it escalates with the record attached. Anything that fails a precondition goes to a person. The aim is to remove obvious bad changes quickly, not to replace human judgment on ambiguous ones.

8. Change observability

Detection is much more useful when the candidate causes are already known. The change observability platform records structural changes across Kubernetes resources, IAM policies and bindings, database schemas and permissions, and network configuration, each with a timestamp, actor and before/after state. It serves three roles in this system: it supplies the candidate change set for correlation in Section 5, it stores the prior state that makes rollback possible in Section 7, and it provides the "principal not seen in baseline" feature in Section 4.1, which is the main signal for unauthorized changes.

9. Evaluation method

We evaluate in three stages, from least to most realistic.

  1. Historical replay. Past telemetry is replayed through detection and correlation with the Act state disabled. Every window the system would have flagged is compared with the incident record. This measures detection precision and recall and the alert reduction relative to raw per-tool alerts.
  2. Shadow mode. The full agent runs on live data and writes its decisions to a log, but never acts. Engineers review its proposed actions against what they actually did. This measures decision quality without production risk.
  3. Fault injection. In a staging environment, known faults are injected (a bad deployment, an over-broad IAM grant, a network policy that blocks a dependency), in the spirit of AIOpsLab [8]. Ground truth is exact, so detection, localization and rollback correctness can be scored directly, including the no-fault case to measure false positives.
MetricDefinition
Alert reduction1 − (agent escalations / raw per-tool alerts) over the same period
Detection precision / recallAgainst incident records (replay) or injected faults (staging)
Time to detectFrom the causal change to the first flagged window
Action precisionShare of automated rollbacks later judged correct by the owning team
False rollback rateRollbacks on no-fault or misattributed windows; the most important number to keep at zero

Measured values are omitted. Cluster names, services and incident data in this report are generalized.

10. Limitations and future work

Baseline drift. Fleet growth, seasonal traffic and new services shift what normal looks like. Refitting on a trailing window helps but lags abrupt shifts; per-service baselines and change-point detection are natural next steps.

Axis artifacts. Standard Isolation Forest can produce score artifacts along feature axes; Extended Isolation Forest [2] is a direct replacement worth evaluating on the same windows.

Model nondeterminism. Two runs on the same evidence can produce different hypotheses. Keeping decisions in code bounds the impact, but hypothesis stability should be measured and reported alongside accuracy.

Learning from history. RCACopilot shows the value of retrieving similar past incidents as demonstrations [6]. Indexing past incidents together with the change observability record would let the agent condition on how similar changes failed before, and let risk classes be weighted by resource type instead of set by hand.

Regression suite. Every resolved incident can become a replay test, so changes to prompts, tools or thresholds are checked against the incidents the system has already seen.
